# Token Export — Compile the Brief, Never Fork It

Load this during **Step 8 (Token Export)**. The creative brief stays the single source of
truth; the token file is a **compilation target** derived from it. Every value in the output
is copied from the brief — nothing is invented here, and nothing here may disagree with the
brief.

## Target Detection

Use the Step 0 project scan (do not re-scan if you already have it):

```
1. package.json lists "tailwindcss" (deps or devDeps)?
   → version starts with 4 (or "@tailwindcss/vite" / "@tailwindcss/postcss" present)
       → Target A (v4 @theme)
   → version starts with 3
       → Target B (v3 preset)
2. No tailwindcss dependency, but the project ships CSS (any .css / <style> in the stack)?
       → Target C (plain custom properties)
3. No CSS surface at all (pure CLI/back-end)?
       → skip Step 8 entirely; tokens have nothing to attach to
```

If the CSS entry point contains `@tailwind base;` directives, treat as v3 even if
package.json is ambiguous. If it contains `@import "tailwindcss";`, treat as v4.

State the detected target and file path to the user before writing anything.

## Output Rules (all targets)

1. **One generated file, never a mutation of user config.** Do not edit
   `tailwind.config.js` theme values or rewrite the user's main CSS. The only permitted
   touch to a user file is the one-line wiring described below.
2. **Generated header is mandatory.** The file must begin with:

   ```
   /* GENERATED by brand-design from docs/pocket/rule/creative-brief.md */
   /* Do not edit by hand — re-run /brand-design (refine mode) to regenerate. */
   ```

   (Use `//` comments for the `.js` preset.)
3. **Values are verbatim from the brief.** Copy the exact OKLCH strings and px sizes the
   brief records. If a value you need is missing from the brief, that is a brief problem —
   go back and fix the brief first (refine mode), never patch it locally in the token file.
4. **Regeneration is overwrite.** The file is disposable output; refine mode rewrites it
   whole. Anything a user hand-added to it will be lost — that is why the header says so.

## Mapping Table (brief → token names)

| Brief section | Token name (v4 / CSS) | v3 preset key |
|---------------|------------------------|---------------|
| Primary ramp 100–900 | `--color-primary-100` … `--color-primary-900` | `colors.primary[100..900]` |
| Neutral ramp 100–900 | `--color-neutral-100` … `--color-neutral-900` | `colors.neutral[100..900]` |
| Semantic bg-tint (L≈0.95) | `--color-success-100` (etc.) | `colors.success[100]` |
| Semantic solid (L≈0.55) | `--color-success-500` | `colors.success[500]` |
| Semantic text-on-tint (L≈0.35) | `--color-success-700` | `colors.success[700]` |
| Type scale xs…3xl | `--text-xs` … `--text-3xl` | `fontSize.{xs..3xl}` |
| Body / heading line-height | `--leading-body`, `--leading-heading` | paired in `fontSize` tuples |
| Font family (from Step 2) | `--font-sans` (or `--font-display` if the brief separates display/body) | `fontFamily.sans` |
| Border radius (from Step 2) | `--radius-brand` | `borderRadius.brand` |
| Atom shadows (sm/md used in state tables) | `--shadow-sm`, `--shadow-md` — only if the brief specifies concrete values | `boxShadow.{sm,md}` |

Apply to all four semantic colors: `success`, `warning`, `error`, `info`.

Naming rules:
- Keep the brief's scale names verbatim — including `md`, which Tailwind does not ship by
  default. `text-md` becoming a real utility is intended behavior, not a bug.
- Overriding Tailwind defaults (`--color-neutral-*`, `--text-sm`, …) is also intended:
  the brand system replaces the stock values so agents cannot reach for off-brand ones.
- Never emit a token for a value the brief does not contain. No padding the file with
  defaults.

## Target A: Tailwind v4 (`@theme`)

**Output path:** `<css-dir>/brand.theme.css`, where `<css-dir>` is the directory of the main
CSS entry point (the file containing `@import "tailwindcss";`).

```css
/* GENERATED by brand-design from docs/pocket/rule/creative-brief.md */
/* Do not edit by hand — re-run /brand-design (refine mode) to regenerate. */

@theme {
  /* Color System — every pair below is WCAG-validated in the brief */
  --color-primary-100: oklch(0.97 0.04 250);
  /* … 200–900 … */

  --color-neutral-100: oklch(0.97 0.01 250);
  /* … */

  --color-success-100: oklch(0.95 0.05 145);
  --color-success-500: oklch(0.55 0.14 145);
  --color-success-700: oklch(0.35 0.1 145);
  /* … warning / error / info … */

  /* Typography — modular scale from the brief */
  --text-xs: 10px;
  --text-sm: 13px;
  --text-base: 16px;
  --text-md: 20px;
  --text-lg: 25px;
  --text-xl: 31px;
  --text-2xl: 39px;
  --text-3xl: 49px;

  --font-sans: "Inter", sans-serif;

  --radius-brand: 6px;
}
```

`@theme` tokens generate utilities (`bg-primary-500`, `text-md`, `rounded-brand`) **and**
are exposed as CSS custom properties — non-Tailwind CSS in the same project can consume
`var(--color-primary-500)` for free.

## Target B: Tailwind v3 (preset)

**Output path:** `tailwind.brand.preset.js` at the project root (next to
`tailwind.config.js`).

```js
// GENERATED by brand-design from docs/pocket/rule/creative-brief.md
// Do not edit by hand — re-run /brand-design (refine mode) to regenerate.

module.exports = {
  theme: {
    extend: {
      colors: {
        primary: {
          100: "oklch(0.97 0.04 250)",
          // … 200–900 …
        },
        neutral: { /* … */ },
        success: { 100: "…", 500: "…", 700: "…" },
        warning: { /* … */ },
        error: { /* … */ },
        info: { /* … */ },
      },
      fontSize: {
        xs: ["10px", { lineHeight: "1.5" }],
        sm: ["13px", { lineHeight: "1.5" }],
        base: ["16px", { lineHeight: "1.5" }],
        md: ["20px", { lineHeight: "1.4" }],
        lg: ["25px", { lineHeight: "1.25" }],
        xl: ["31px", { lineHeight: "1.2" }],
        "2xl": ["39px", { lineHeight: "1.1" }],
        "3xl": ["49px", { lineHeight: "1.1" }],
      },
      fontFamily: {
        sans: ["Inter", "sans-serif"],
      },
      borderRadius: {
        brand: "6px",
      },
    },
  },
};
```

Use `theme.extend` (not bare `theme`) so the preset merges on top of defaults instead of
deleting scales the project may already use. Match the config's module system: emit
`export default` instead of `module.exports` if `tailwind.config` is ESM (`.mjs` or
`"type": "module"`).

Note: OKLCH strings in v3 configs work, but `bg-primary-500/50` opacity modifiers will not
apply to them (v3's opacity plumbing predates OKLCH). Mention this caveat to the user when
emitting Target B.

## Target C: No framework (plain CSS custom properties)

**Output path:** `<css-dir>/tokens.css` (or `styles/tokens.css` if no obvious CSS dir).

Same variables as Target A but in `:root { … }` instead of `@theme { … }`. This target
generates no utilities — it only gives hand-written CSS one canonical place to pull brand
values from (`color: var(--color-primary-700)`).

## Wiring the File In (idempotent)

The single permitted edit to a user file, guarded so re-runs never duplicate it:

**Target A** — in the main CSS entry point, immediately after `@import "tailwindcss";`:
```
grep -qF '@import "./brand.theme.css";' <entry.css> || add the line
```

**Target B** — in `tailwind.config.js`, add to `presets`:
```js
presets: [require("./tailwind.brand.preset.js")],
```
Check the config first: if a `presets` array exists, append only when the entry is absent;
if none exists, add the key. If the config is too unusual to edit confidently (computed
config, wrapped in a function), do NOT guess — emit the preset file and give the user the
exact one-line instruction instead.

**Target C** — add `@import "./tokens.css";` at the top of the main stylesheet, or a
`<link>` tag if there is no CSS entry point; same grep-first guard.

After wiring, tell the user exactly which file was created and which line was added where.

## What Tokens Do NOT Cover

Be explicit with the user about this boundary:

- **Atom state tables** (Button Hover/Focus/Disabled/Error, etc.) — states compose multiple
  tokens plus behavior; they stay in the brief and are implemented per component.
- **Molecules and copy guidelines** — brief only.
- **Contrast guarantees** — the tokens carry validated values, but new combinations an
  implementer invents (`text-primary-300` on `bg-primary-100`) are not auto-validated.
  The brief's validated-pairs list remains the authority for which combinations are legal.

The SessionStart hook (Step 7) still points agents at the brief. Tokens make the brief's
values *reachable* in code; they do not replace it.

## Validation Checklist

Before finishing Step 8:

```
[ ] Target detection stated to the user (framework, version, output path)
[ ] Generated file starts with the mandatory GENERATED header
[ ] Every token value matches the brief verbatim (spot-check primary-500, base size, radius)
[ ] No token exists that has no corresponding brief value
[ ] Wiring line added exactly once (grep-first), or explicit instruction given instead
[ ] User told what tokens do NOT cover (atom states, copy, unvalidated combinations)
```
